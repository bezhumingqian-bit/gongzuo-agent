# 产品简述：开源企业内部应用 Agent

状态：讨论稿（2026-09-22）

## 一句话定位

一个可自行部署的企业内部应用生产与运行平台：Agent 根据自然语言需求编写真实代码，团队审阅、发布、使用并持续维护这些小应用。

这里的交付物是**长期运行的软件**。报表、脚本和文件可以是应用的一部分，但首版是否成功，要看同事能否持续使用同一个应用，数据和版本能否安全延续。

## 为什么采用这个方向

用户的产品判断：个人 Agent 的线性对话适合发起工作，但随着参与者和历史任务增加，企业需要共享的软件入口、责任归属和可管理的生命周期。这个判断合理，但仍需真实团队验证。

相邻产品已经覆盖部分能力：

| 产品 | 官方资料显示的能力 | 本项目需要进一步验证的空间 |
| --- | --- | --- |
| [WorkBuddy](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Product-Guide) 与 [企业版](https://cloud.tencent.com/product/workbuddy-enterprise) | Agent 自主执行办公任务；企业版提供组织管理、审计和私有化 | 从任务结果进一步走向团队长期使用的内部应用 |
| [Retool](https://docs.retool.com/) | 提示词生成应用，并提供企业应用构建、部署和治理 | 开放源码、自行部署与 Agent 持续修改应用的完整体验 |
| [Appsmith](https://docs.appsmith.com/) | 开源内部应用构建、数据连接、Git 协作、部署和共享 | 自然语言驱动的代码生成与持续维护体验 |

上表最后一列是产品假设，并非对竞品缺失功能的断言。项目不能仅以“WorkBuddy 企业版”或“AI 生成页面”作为差异点。

## 三类界面

| 界面 | 主要使用者 | 核心内容 |
| --- | --- | --- |
| 工作主页、Agent 与任务页 | 员工、构建者 | 可切换模块工作台、简洁概览和 Agent 输入界面；在任务对话旁查看进度与成果 |
| 团队空间 | 团队成员 | 共享任务、已发布应用、按分类和标签管理的知识 |
| 管理设置 | 管理员 | 成员与角色、模型和工具配置、发布记录、应用运行状态 |

产品主对象是**应用**：每个应用有源码、配置、数据、权限、版本、运行实例和负责人。对话记录附属于应用及其变更请求。应用使用者无需阅读构建对话。员工端详细交互见 [员工交互设计](EMPLOYEE_EXPERIENCE.md)。

## 首版纵向流程

1. 构建者描述一个内部应用需求，并提供示例数据或字段说明。
2. Agent 在按应用隔离的开发环境里生成前端、后端或数据模型，并运行检查。
3. 构建者预览界面、查看拟新增的数据结构和权限，要求修改或批准发布。
4. 发布器产生不可变版本，将它部署到内部访问地址；旧版本保持可回滚。
5. 使用者按角色登录，使用应用并写入持久数据。
6. 构建者提出新需求，Agent 修改现有源码；通过检查和审批后发布新版本。

首版只支持一种受约束的应用技术栈和平台托管的数据存储，避免任意生成代码直接接触企业网络或数据库。具体技术栈在原型阶段确定，并应允许导出源码。

## 必须明确的边界

- **开发与运行分开**：Agent 写代码的沙箱和应用实际运行环境隔离。
- **发布是受控动作**：发布前展示代码差异、数据结构变化、依赖及权限变化，并由人确认。
- **数据随应用持续存在**：发布新版本不清空业务数据；结构迁移必须可检查并有备份。回滚代码版本不等于自动回滚数据。
- **访问按应用控制**：平台在生成代码之外强制检查身份和权限；构建者、管理员和普通使用者的能力分开。
- **失败可恢复**：构建或发布失败不影响在线版本；保留代码版本与回滚路径。
- **源码可带走**：生成结果是可检查、可导出的代码，避免只能在平台内使用。

## MVP 验收场景

演示需求：“做一个客户反馈管理应用。员工能录入反馈、按状态筛选、更新处理状态；管理员能看到汇总。”

验收检查：

1. Agent 生成应用后，构建者能在隔离预览中检查界面和操作。
2. 发布后，两名不同角色用户能访问各自获准的页面与操作，并共享持久数据。
3. 第二次需求要求增加统计页，新版本保留原有反馈数据。
4. 失败更新不会替换线上版本；回滚后应用仍可用，数据处理方式清楚记录。
5. 从需求到发布的代码、测试结果、审批人、版本与运行状态可追溯。

## 先验证的问题

- 哪类团队有大量“小而持续存在”的内部应用需求？他们现在如何提出需求、开发和维护？
- 他们更在意首次生成速度，还是后续修改、数据安全、权限与可交接性？
- 构建者愿意审阅多少代码与配置？哪些变化必须交给开发者或管理员批准？
- 开源和自行部署对目标团队是否是实际采购条件？

建议访谈 3–5 个有内部工具需求的团队，用上述闭环原型验证。首要指标是：从需求到首次可用版本的时间、一次修改到再次发布的时间、上线后人工修复次数，以及数据或权限事故数。
