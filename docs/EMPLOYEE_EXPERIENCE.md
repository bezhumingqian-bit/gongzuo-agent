# 员工视角的交互设计

状态：讨论稿（2026-09-23）。依据用户提供的 WorkBuddy 界面截图与反馈整理；当前 macOS MVP 已实现首页模式原型，仍需员工测试。

## 员工打开产品时应先看见什么

员工打开的是持续工作的桌面应用。主页可选**工作台、简洁、Agent** 三种模式：工作台汇集当前员工的待办、可见的空间工作、外部接入状态、空间资料和最近工作；简洁模式只保留关键数字与待处理列表；Agent 模式保留直接说出目标的输入界面。三种模式都能一键发起新工作，任务仍在同一个对话中承载执行过程、团队协作和成果。

```text
┌────────────────────── 桌面 Agent 窗口 ──────────────────────┐
│ 窗口控制                               通知 / 当前参与者     │
├ 图标栏 ┬ 可收起的会话栏 ┬───────────────────────────────────┤
│ 主页   │ 最近的工作     │  工作台 / 简洁 / Agent            │
│ 工作   │ 需要我处理     │  [可配置的工作模块]                │
│ 空间   │                │  [发起新工作]                      │
│ 应用   │                │  或直接进入 Agent 输入界面         │
└────────┴────────────────┴───────────────────────────────────┘
```

顶部的 Agent 标志承担“主页”入口，点击后返回员工选择的默认首页；首页内的“发起新工作”进入 Agent 输入界面。其余常驻入口是**我的工作、工作空间、团队小应用**，点击后打开轻量抽屉。“我的工作”只收录员工发起、参与、被指派，或 Agent 正在替该员工执行的工作；“最近参与”按项目、团队等工作范围收拢，默认只展开最近的一个范围并显示少量工作，后续 AI 对话留在原工作内部。团队共享内容从“工作空间”进入。员工不必先选助理、项目或工作流。当前工作空间决定 Agent 可见的团队资料、小应用和外部信息来源。

在一项工作中需要同事处理事情时，员工可在对话框输入 @ 或点击“@ 同事”，从当前空间的成员中选择收件人；消息会保留提及的成员 ID、正文、任务位置与送达状态。只有已经加入当前空间的成员可被正式提及，待邀请成员不能被当成已送达。当前单机 MVP 尚无账号和通知服务，提及只记录为“未送达”；浏览器提供演示成员，但不会真实发消息。接入团队账号后，应用内通知应将收件人直接带回对应工作消息，外部渠道可作为补充提醒。

主页默认收起左侧抽屉，让模块成为主要内容；需要查找完整工作列表时再打开“我的工作”。

工作台的模块可显示、隐藏和排序；三种主页模式的右上角都可打开“自定义模块”，切回工作台即可查看布局变化。首页模式与模块布局先保存在当前设备上，不改变团队其他成员的界面。当前 MVP 的“待我处理”来自本机可见任务，“当前空间工作”只统计本机可见且归属当前空间的任务；它们还不是组织全量统计。外部接入模块只显示真实连接数量，未接入时为 0。正式团队版应按组织账号与空间权限从服务端提供数字，再支持按角色分发团队默认布局。

## 四个核心对象

| 对象 | 作用 | 放在哪里 |
| --- | --- | --- |
| 工作空间 | 团队、项目或公共范围内的任务、资料、记忆与成员容器 | 左侧“工作空间”按团队、项目、公共分组；发起工作时在输入框旁选择归属空间 |
| 工作任务 | 一个目标和它的执行过程，包含参与者、状态、关键决定与成果 | 连续 Agent 对话；左侧“我的工作”找回个人相关任务，团队空间查看共享任务 |
| 团队小应用 | 团队成员让 Agent 制作并发布、供同事长期使用的工作工具，含版本、数据和权限 | 左侧选中应用后，右侧主区域直接显示应用；任务中的成果在对话右侧预览和确认 |
| 知识 | 人维护的文档和说明，按分类与标签组织 | 工作空间右侧展示该空间的资料，可上传、搜索和管理；任务内按需引用 |

**项目空间**从“工作空间 → 新建项目”创建，可关联一个团队用于归类，但资料和成员独立管理，不自动继承团队访问权限。创建者是负责人；创建后的第二步可按邮箱添加待邀请成员，并设置只读或协作权限，之后仍可修改待邀请成员的预设权限。项目空间展示项目工作、资料和记忆。当前本机 MVP 尚未接入企业账号，待邀请名单不会发送给同事，也不会授予真实访问权限。项目仍在“空间”中，不增加全局“项目”主入口。**助理**不是员工必须管理的独立对象：任务内始终可以调用 AI，任务上下文决定它能做什么。

左下角“连接与模型设置”分为模型、执行 Agent、企业微信三个配置区。员工可登记服务地址、模型 ID、企业微信应用与智能机器人标识；密钥仅在 Mac 客户端加密保存。界面将“配置已保存”与“连接测试通过”分开显示。Mac 版能调用 OpenAI 或兼容模型、外部 Agent；企微自建应用可定向通知与同步可见成员，智能机器人可按已关联的空间成员权限新建和更新工作。真实企业账号端到端验证与跨设备项目访问尚未完成。详细边界见[连接与测试范围](CONNECTIONS.md)。

## 个人长期记忆与团队记忆

长期记忆独立于任务对话保存。任务保留完整过程；记忆只保留以后仍有用、能够用一句话说明的事实或约定。员工在任务里点“提炼记忆”，检查并修改草稿，再明确选择保存为个人或团队记忆。聊天或邮件内容进入系统后也遵循这一流程，不把整段聊天自动变成记忆。

| 范围 | 适合保存 | 谁可以使用 | 放在哪里 |
| --- | --- | --- | --- |
| 个人记忆 | 本人的表达偏好、常用工作方式、个人职责背景 | 本人的 Agent 工作；不随团队任务共享 | 个人入口 |
| 团队记忆 | 已确认的术语、流程、决定、项目背景与验收约定 | 所属工作空间中获授权的成员和 Agent | 工作空间 |

每条记忆显示来源任务、分类、标签、确认人和修订记录。员工可以修改或移出；移出后不再用于新工作。对相互矛盾或可能过期的团队记忆，后续版本应提出复核，而不是默默覆盖。团队记忆的发布、撤销和权限变动需要审计。

首版不增加独立的左侧导航入口：工作空间抽屉并列展示个人记忆和团队记忆，头像也能直达个人记忆；当前任务有“提炼记忆”。记忆采用分类、标签和关键词定位；未来确有规模需求时再增加语义检索。团队资料库保留原始文档，长期记忆保存从文档或任务中确认过的要点，两者都应能回到来源。

当前 macOS MVP 把两类记忆保存在本机的独立文件中，已能验证提炼、确认、修订、归档与按空间筛选。它还没有组织登录和团队同步，因此其他成员暂时看不到这台 Mac 上的团队记忆。正式团队版需要把团队记忆存入企业服务端，并按成员身份和工作空间权限读取。

## 从想法到长期使用的应用

1. **发起工作**：员工输入目标，选择团队空间；若在某项目内发起，项目自动成为上下文。
2. **选用范例**：系统按目标推荐最佳实践模板，展示实际完成效果、需要提供的资料、通常的步骤和验收标准。员工可以直接修改模板内容，也可以从空白开始。
3. **形成任务**：页面显示目标、负责人、参与者、AI 当前步骤与下一步。AI 只在缺少关键条件时追问；资料和权限在任务中明确可见。
4. **制作应用**：AI 在隔离环境里编写代码。任务主区域展示应用预览、变更和验收结果；对话用于指导修改，执行日志按需展开。
5. **审阅发布**：有发布权限的人确认数据结构、访问范围和变更。发布后，应用出现在团队空间的应用页，获授权员工直接使用。
6. **持续改进**：应用内提供“提出改进”入口，生成关联到该应用的新任务。新版本沿用原有数据和权限，经审阅后发布，并保留回滚路径。

员工日常使用已发布应用时，不必进入 Agent 对话。需要 AI 帮忙时，可以从应用页面发起关联任务，已有上下文自动带入。

飞书、企业微信和邮件等外部沟通渠道作为任务的信息来源。获得授权的消息可以进入任务时间线；低风险进度允许自动更新并提供撤销，高影响字段先由负责人确认。详细规则见[沟通渠道接入设计](CHANNEL_INTEGRATIONS.md)。

## 工作中的 Agent

```text
标题 / 当前团队 / 参与者 / 成果按钮
┌ 连续对话与执行过程 ─────────────────┬ 按需打开的成果面板 ───────┐
│ 员工目标、AI 步骤、解释与反馈        │ 预览 / 改动 / 检查        │
│ 追加要求、邀请同事、确认发布         │ 数据与权限变化            │
│ 输入框始终可见                      │ 可直接操作的生成应用       │
└─────────────────────────────────────┴─────────────────────────┘
```

任务仍有状态与责任，但不表现为工单详情页。主区域保持 Agent 的核心循环：**提出目标 → 看执行 → 修改方向 → 审阅成果**。成果面板按需打开；在窄窗口中覆盖主区域，关闭后立刻回到对话。接手成员可以看到结构化步骤和关键决定，不必重读完整聊天记录。

## 对截图中功能的处理

| WorkBuddy 中的入口 | 本方案中的位置 |
| --- | --- |
| 新建任务、任务、置顶任务 | “开始一项工作”和最近工作；置顶成为收藏或筛选，不另起区块 |
| 空间 | 保留为“团队空间”，承担共享和权限边界 |
| 项目 | 放在空间内部，按成员关系呈现项目概览 |
| 助理 | 收入任务内的 AI 能力，不要求员工选择或创建助理 |
| 资料库 | 空间内的“知识”：分类、标签、关键词搜索、权限；首版不做向量检索或 RAG 配置 |
| 定时任务 | 相关任务的“重复执行”或应用的“运行计划”，不设独立主页 |
| 专家、技能、连接器 | 管理员配置中统一管理；Agent 需要未授权能力时，在当前任务提出请求 |
| 更多 | 不作为功能收纳入口；低频功能放到其所属对象的设置中 |

## 吸收 WorkBuddy 的长处

模板是一份**可查看的完成案例**，不是一串抽象指令。每份模板至少给出：适用场景、输入样例、最终效果、关键步骤、验收标准和常见风险。员工选择模板后，它填入任务目标与验收标准；AI 可以按具体情况调整实现。团队可以把成功的应用和任务过程整理成内部模板，经人审核后共享。

首页只展示与当前工作相关的少量模板；完整模板集合通过“发起工作”时的搜索和筛选进入，避免再增加左侧导航项。

## 需要用原型验证

- 员工能否在 5 秒内看出自己下一步要做什么？
- 新成员能否通过任务页接手工作，而不用重读聊天记录？
- 员工能否从应用中发起修改，并理解修改会影响哪些人和数据？
- 团队是否真需要“项目”这一层，还是空间加标签已足够？
- 模板展示“完成效果”是否比单纯列出模板名称更容易让员工开始？
