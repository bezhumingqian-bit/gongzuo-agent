# 沟通渠道接入与任务自动更新

状态：讨论稿（2026-09-23）。目标是让任务跟随真实工作自动变化，同时保留来源、权限和撤销能力。

## 产品判断

企业沟通工具应当成为 Agent 的输入渠道，而不是员工需要进入的新模块。员工继续在飞书、企业微信或邮件里工作；系统把获得授权的消息关联到已有任务，并在任务时间线里留下带原文来源的进展事件。

“自动更新”分为三层：

| 层级 | 系统动作 | 例子 |
| --- | --- | --- |
| 自动归档 | 消息关联到任务，不修改业务字段 | 讨论方案、补充背景、发送附件 |
| 自动更新，可撤销 | 修改低风险、可逆的进度项，同时显示原文与撤销入口 | 任务负责人明确说“接口已经联调完成” |
| 建议更新，等待确认 | Agent 生成变更建议，由负责人确认 | 改负责人、改截止时间、标记整个任务完成、对外发布 |

不要仅依赖模型置信度。是否自动执行还要看消息发送者、消息所在群、任务绑定关系、字段风险和企业策略。

## 员工看到的交互

渠道配置不进入主导航。管理员负责安装企业应用和授权范围，团队负责人把某个群、邮箱标签或邮件地址绑定到团队空间或具体任务。

任务对话中显示一张来源卡片：

```text
飞书 · 客户反馈项目群 · 王宁 · 8 分钟前
“统计口径没有问题，可以发布。移动端支付的问题今天也处理完了。”

✓ Agent 已自动更新进展
  “确认统计口径”已完成 · 原文已作为依据        [撤销]
```

用户点“查看原消息”可以回到原渠道。撤销只撤销任务字段变化，不删除原始消息或审计事件。

渠道消息进入任务时间线后，Agent 可以另外提出“值得长期记住”的候选内容。例如反复出现的团队术语、经负责人确认的决策或稳定流程。候选内容必须显示原消息来源，并由人选择个人或团队范围、编辑并确认；普通聊天与一次性进度不自动进入长期记忆。

## 接入可行性

| 渠道 | 可用机制 | 首版建议 |
| --- | --- | --- |
| 飞书 | 企业自建应用可以通过事件订阅接收消息；接收范围取决于机器人能力与租户授予的权限，可以使用长连接或 Webhook | 最适合作为第一个聊天渠道，先支持指定群与机器人单聊 |
| 企业微信 | 智能机器人可通过 WebSocket 长连接收发可见会话中的消息；自建应用可提供成员目录与应用通知；更广的员工和客户聊天同步通常依赖“会话内容存档”、管理员配置与合规告知 | 首版用 BotID 与 Secret 接入智能机器人，只处理发给机器人的消息；成员目录作为高级配置 |
| 微信 | 官方开放能力主要围绕公众号、小程序、客服等业务主体；不把个人微信完整聊天同步作为产品承诺 | 只做有明确官方接口的场景，例如公众号或客服消息 |
| Gmail | `users.watch` 通过 Cloud Pub/Sub 通知邮箱变化，再用 `history.list` 拉取增量消息 | 支持指定标签或转发地址，避免默认读取整个邮箱 |
| Microsoft 365 邮箱 | Microsoft Graph 可以订阅用户邮箱或特定邮件文件夹的消息变化，并向 Webhook 推送通知 | 与 Gmail 同级支持，优先指定文件夹或共享邮箱 |
| 其他邮箱 | IMAP IDLE、定期增量同步或专用转发地址 | 作为通用兼容方案，能力低于原生 OAuth 接入 |

飞书的接收消息事件和事件订阅机制见[飞书开放平台](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive)。Gmail 支持通过 `watch` 和 Pub/Sub 接收邮箱变化，但订阅需要续期，再用历史记录接口读取具体增量，见 [Gmail push notifications](https://developers.google.com/workspace/gmail/api/guides/push)。Microsoft Graph 支持对邮件消息创建变更订阅，见 [Outlook change notifications](https://learn.microsoft.com/en-us/graph/outlook-change-notifications-overview)。

## 数据处理流程

```text
渠道事件
  → 验签、解密、去重
  → 标准化消息与附件
  → 映射企业成员身份
  → 匹配团队空间 / 群 / 邮件线程 / 任务
  → 提取进展、决定、风险和待办
  → 策略引擎决定：归档 / 自动更新 / 请求确认
  → 写入任务事件和可追溯依据
```

核心记录至少包括：`source`、`tenant_id`、`conversation_id`、`message_id`、`sender_identity`、`occurred_at`、`task_id`、`quoted_evidence`、`proposed_patch`、`decision`、`decided_by` 和 `reverted_at`。原始消息与提取后的任务更新分开存储。

## 自动更新策略

首版只开放以下自动更新：

1. 指定群或邮件线程已经显式绑定到任务。
2. 发送者能映射到企业成员，并且有权修改该任务。
3. 消息包含明确完成语句和可定位的任务步骤。
4. 更新属于布尔进度、补充说明或证据附件。
5. 每次更新都可撤销，并在任务时间线中显示原文与来源。

以下变化必须确认：任务整体完成、负责人、截止时间、访问权限、预算、对外发送和应用发布。多条消息相互矛盾时停止自动更新，生成“需要确认”的摘要。

## MVP 顺序

1. 飞书自建应用：指定群消息和机器人单聊，手动绑定任务。
2. 消息归档、任务建议更新、确认和撤销；先收集准确率。
3. 对明确完成语句开放少量自动更新。
4. Gmail 与 Microsoft 365：指定标签、文件夹或共享邮箱。
5. 企业微信：从显式发给智能机器人的消息开始，根据客户是否已有会话存档许可决定是否扩展。
6. 微信：仅实现客户明确需要且官方开放的公众号、客服或小程序场景。

首版指标包括：消息到任务的正确关联率、建议更新采纳率、自动更新撤销率、漏掉的重要进展数，以及从聊天发生到团队任务可见的延迟。

## 通知同事：@ 即通知（2026-10-14）

结论：共作的输入框只交给 Agent，不做“直接发企微”。外发只有一种语义：**@ 同事 = 通知他来看这项工作**；Agent 的回复需要给谁，在回复上点“转发给…”。群播报暂不做，需要时直接让 Agent 去拉群。

### 通道与优先级（企微是主通道）

| 通道 | 用途 | 是否要求对方先互动 | 优先级 |
| --- | --- | --- | --- |
| 企微自建应用 | 通知同事（@、指派、转发） | 不需要，应用可见范围内即可 | 1（主通道） |
| 飞书自建应用 | 通知只用飞书的同事 | 不需要，应用可用范围内即可 | 2（可选） |
| 企微智能机器人 | 同事在企微里使用共作；仅在自建应用未配置时兜底通知 | **需要**：对方先给机器人发过消息（[官方说明](https://developer.work.weixin.qq.com/document/62158)） | 3（兜底） |

路由在 `electron/channel-router.cjs`：按成员绑定的账号挑第一个可用通道，结果记录在消息上（`mentionDeliveries` / `forwards`，含 `channel`）。

### 身份绑定
- 我：设置 → 连接器 → 我的身份（名字、企微 UserID、飞书 ID），同事收到“某某 在共作 @ 了你”。
- 同事：空间「成员」里从企微通讯录添加（自建应用同步可见成员）；用飞书的同事在同一处绑定飞书邮箱 / user_id / open_id。
- @ 列表展示这项工作归属空间与关联空间的全部成员，并标出“会发到企微 / 飞书”；未绑定或通道未配置的成员不可选，并说明原因。

### 消息格式
- @：`某某 在共作「工作标题」中 @ 了你：正文 + 打开工作链接`
- 转发：`某某 从共作「工作标题」转发给你 Agent 的回复：正文 + 链接`
- 超过 2048 字节截断并注明“完整内容见共作”。
